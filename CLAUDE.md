# Puppet Alert Orchestrator — Codebase Guide

This document is the source of truth for conventions, architecture decisions, and "how we do things here." It is intended to be read by both humans and AI before touching code.

## What this repo is

A Splunk add-on that triggers Puppet Enterprise Orchestration actions (run task, run plan, generate detailed report) from Splunk alert conditions. It is published to Splunkbase and deployed to Splunk Enterprise and Splunk Cloud.

## Build system

This add-on uses the [Splunk UCC Framework](https://splunk.github.io/addonfactory-ucc-generator/) (`ucc-gen`).

```bash
# Install all dev deps (includes ucc-gen and slim)
pip install -r requirements-dev.txt

# Install runtime deps into lib/ (where Splunk finds them)
pip install -r requirements.txt --target TA-puppet-alert-orchestrator/lib

# Build
ucc-gen build --source TA-puppet-alert-orchestrator --overwrite

# Package (for local testing or manual Splunkbase upload)
slim package output/TA-puppet-alert-orchestrator
```

**`output/` is fully generated — never edit it and never commit it.** The build overwrites it entirely. The CI release workflow runs both `ucc-gen build` and `slim package` automatically on version tag push.

## Source of truth for forms and configuration

`globalConfig.json` at the **repo root** drives everything UCC generates:
- The configuration page (Account, Logging, Add-on Settings tabs)
- Alert action HTML forms (field labels, types, help text, dropdowns)
- REST handler conf files
- Spec files under `README/`

When adding or changing a form field, start in `globalConfig.json`. Do not create or hand-edit `default/data/ui/alerts/*.html` — those files are generated by `ucc-gen build`. If they exist in source they will override the generated ones (and break things).

Default parameter values for alert action fields belong in `default/alert_actions.conf` as `param.<name> = <value>` — the `defaultValue` in `globalConfig.json` is display metadata only and does not affect Splunk runtime behavior.

```
    alert_actions.conf.spec           # Documents alert action parameters
  bin/
    inputs/orchestrator_actions.py    # Indexes PE tasks/plans into Splunk via HEC

```

## Alert action pattern

Every alert action has exactly three layers:

| Layer | File | Role |
|---|---|---|
| Entry point | `bin/puppet_run_task.py` | Generated by UCC — do not touch |
| Helper | `bin/ta_puppet_alert_actions/modalert_puppet_run_task_helper.py` | `process_event()`: reads params, resolves settings via `override()`, calls action layer |
| Action | `bin/ta_puppet_alert_actions/puppet_task_action.py` | Makes the actual PE API call, posts result to HEC |

The helper uses two shared utilities (defined per-helper, not imported):
- `override(setting_name, helper)` — returns the alert-level param if set and non-empty, falls back to the global add-on setting
- `notnone(default, possible_none, helper)` — returns `possible_none` if truthy, otherwise `default`

## The `pie/` library

Internal library for PE and Splunk API communication. All functions accept `ssl_verify` (bool) which maps to the **Verify SSL Certificate** add-on setting.

| Module | Responsibility |
|---|---|
| `pie/orch.py` | Puppet Orchestrator: list tasks/plans, request jobs, get results |
| `pie/pdb.py` | PuppetDB: fetch report data |
| `pie/rbac.py` | PE RBAC: generate auth tokens |
| `pie/hec.py` | Splunk HEC: post action events |
| `pie/util.py` | Derive PE service URLs from console hostname |

Do not add Splunk SDK calls or REST handler logic into `pie/`. Keep it focused on PE/HEC communication.

## Python conventions

- Python 3 only. No Python 2 compatibility shims.
- Use `!= ''` not `is not ''` for empty string checks — `is not` compares identity, not value.
- No bare `except:` — always catch a specific exception or at minimum `Exception as e`.
- The `lib/` directory is on the path at runtime. Do not use `aob_py3/` or any other vendored path — that directory no longer exists.

## Version

Version is set in three places and must be kept in sync:
- `globalConfig.json` → `meta.version`
- `TA-puppet-alert-orchestrator/default/app.conf` → `[id] version` and `[launcher] version`
- `TA-puppet-alert-orchestrator/app.manifest` → `info.id.version`

`ucc-gen build` appends the short git SHA to the `globalConfig.json` version by default (e.g. `2.0.0+a1b2c3d`). The release workflow passes `--ta-version` (derived from the pushed tag, with the leading `v` stripped) so the packaged artifact carries the clean semver. The source `globalConfig.json` should still contain only the clean semver.

## CI

- **validation.yml** — runs on every PR to `main`. Builds with `ucc-gen`, uploads `output/` as an artifact, then runs `splunk-appinspect` in a separate job using the custom container at `ghcr.io/coreymbe/splunk-appinspect`.
- **release.yml** — runs on version tags (`v*.*.*`). Builds and packages with `slim`, uploads the `.tar.gz` as a GitHub Actions artifact.

## Adding a new alert action

1. Add the action definition to `globalConfig.json` under `alerts` — fields, types, labels, help text
2. Add the stanza to `default/alert_actions.conf` with any `param.<name> = <default>` entries
3. Add the stanza to `readme/alert_actions.conf.spec`
4. Create `bin/ta_puppet_alert_actions/modalert_<name>_helper.py` with `process_event(helper, *args, **kwargs)`
5. Create `bin/ta_puppet_alert_actions/<name>_action.py` with the PE API logic
6. Run `ucc-gen build --source TA-puppet-alert-orchestrator --overwrite` — the entry point and HTML form are generated automatically
